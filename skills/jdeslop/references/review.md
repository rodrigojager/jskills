# Visual review

For an audit and a review together, continue the [jdeslop CLI run](coverage.md#combined-cli-run). Use its `coverage.json`, `review.json` and recorded source root. For a standalone review of existing audit files, use the builder or server directly. Keep catalog IDs, findings, exceptions and evidence gaps. Use the approved product direction. Prioritize small corrections supported by the evidence.

1. Capture one faithful HTML baseline and ledger surface for each relevant route or state. Include representative instances of a shared component or rule in the same review. Retain real content and standalone styles and assets. Label the state, fixture and any fidelity limits. Keep sensitive data out of shareable artifacts.
2. Prepare the [review manifest](../review/references/review-format.md). Link each correction to its findings and show it on every affected snapshot in scope. Order dependencies before their consumers. Keep evidence gaps and findings without a faithful visual proposal visible in Coverage. For live approval with source access, prepare the exact source edits for each revision up front. Test each source change in isolation, then test the cumulative order and the actual affected UI behavior.
3. Start `jdeslop review <run>` for the shared run, with `--portable` for an HTML preview. For a standalone review, build the preview with `python <skill>/review/scripts/build.py review.json review.html`, or use `python <skill>/review/scripts/serve.py review.json --source-root <product> --state <review-folder>/queue.sqlite3` to enable the source queue. Inspect **Original**, **Before fix** and **After fix** at narrow and wide widths and relevant breakpoints. Turn off **Include earlier fixes** to check the selected fix with its prerequisites only. Resolve missing or ambiguous targets. Label a trusted `liveUrl` when available so the reviewer can exercise the real product.
4. Deliver the review URL or file. In a portable preview, **Keep** records visual acceptance and the agent applies only separately authorized choices. In the local server, **Approve and queue** applies the prepared revision in the background, and **Approve and queue all** applies remaining eligible corrections. Skipped corrections, revisions returned for adjustment and dependents of either stay out of the batch. The queue tracks exact revisions across reloads. Review **Applied**, **Failed**, **Waiting for prerequisite**, **Blocked**, and **Interrupted** before reporting progress.
5. For requested changes or conflicts, inspect current source, retain the correction ID, increment its revision and regenerate the preview and source edit together. Restart the server with the same review ID and queue database. The export records revision-bound decisions and notes. Imports restore review decisions without starting source jobs.
6. Re-render applied changes in the actual product. Verify affected behavior, shared routes and responsive widths, and record fresh evidence separately from the approved baseline and findings. **Applied** means the prepared source edit was written. The shared CLI's `status` reports this queue state.

The [example](../review/examples/review.json) shows a spacing fix, removal of redundant copy, reordering of a payment action and a separately reviewable copy edit. Build it with the same command.
