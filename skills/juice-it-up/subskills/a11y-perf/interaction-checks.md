# Interactive behavior checks

Use this checklist on in-scope widgets in the full diagnostic pass, on widgets affected by a motion or seasonal change, and again when reviewing the mock and the implementation. Identify the widget's purpose and supported interactions first. Prefer native HTML and the project's existing components when they provide the expected behavior. Use the corresponding ARIA pattern for custom widgets. These checks work with any framework or with plain HTML, CSS and JavaScript. [WAI-ARIA Authoring Practices](https://www.w3.org/WAI/ARIA/apg/patterns/), [Vercel UI SDK behavior catalog](https://ui-sdk.dev/)

| Check ID | What to exercise on the rendered surface |
| --- | --- |
| `semantics` | Inspect role, accessible name and description, visible label, and applicable states. Activate the control and verify attributes such as `aria-expanded` or `aria-pressed` follow the actual UI. Check that ARIA references resolve in every state where they apply, icons convey no redundant label, and hidden content contains no reachable focus stops. |
| `activation` | Activate actions and links with their expected keyboard and pointer inputs. Verify one action per activation and try a disabled or pending state. Custom controls using `aria-disabled` must enforce that state in their handlers. |
| `tab-order` | Traverse with Tab and Shift+Tab, including after the UI changes. Verify a logical order, visible focus that stays in view, and a way past repeated navigation where applicable. Check that hidden or collapsed controls are skipped. |
| `composite-keys` | Enter a tablist, listbox, menu, toolbar or grid with Tab, navigate with the keys specified for its pattern, and leave it in both directions. Check orientation, arrow keys, and Home/End where applicable. Verify that roving `tabindex` or `aria-activedescendant` keeps the intended item active and that editable controls retain their standard text-editing keys. |
| `focus-lifecycle` | Open and close the widget using its supported paths. Verify sensible initial focus, focus restoration to the opener or a logical fallback, and a usable focus position when an active item is removed, hidden, filtered or replaced. |
| `selection` | Move focus without committing a choice where the pattern distinguishes the two. Select, change and clear a choice where supported. Test single selection, multiple selection and range selection where provided. Check that the visible and accessible selected, checked or current state reflects the value committed by the user. |
| `typeahead` | Test typed navigation or filtering where supported. Cover a match, no match, clearing and an asynchronous update if applicable. In an editable combobox, verify that editing continues to work, old responses cannot overwrite newer results, and Enter or Escape has the pattern's expected effect on the current value. |
| `dismissal` | Verify the overlay's actual kind. In a modal, background content is inert, keyboard focus stays within the modal while open, and an accessible close control is available. A keyboard user can leave a nonmodal popup. Exercise Escape on the topmost dismissible layer, the explicit close action and outside interaction where supported. Check that dismissing an unfinished action does not silently commit it. |
| `popup-placement` | Open an anchored popup near viewport and scrolling-container edges. Check narrow layout, zoom and touch. The trigger and interactive content stay usable, and scroll or resize keeps the popup anchored or dismisses it according to its behavior. |
| `tooltip` | Trigger the same help via pointer and keyboard focus. Ensure it can be dismissed and remains readable when the pointer moves onto it where required. Use an appropriate interactive popup for content with actions. |
| `drag-reorder` | Try a valid drop, cancellation and an invalid drop. Check the result, focus and position feedback. For nonessential dragging, provide a single-pointer path without dragging, such as Move up and Move down buttons, and verify the equivalent keyboard operation. Confirm the order after reload if the feature persists it. [WCAG 2.2 dragging movements](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html) |
| `adjustment` | For sliders, resize handles or pan/zoom, check the documented keyboard operations and non-drag alternatives where required. Verify the current value, direction, bounds, and feedback. Try touch input without disabling unrelated page scrolling or zoom. |
| `forms-status` | Exercise validation, pending, failure and success where applicable. Check field names and error associations, a clear way to correct errors, and that draft input survives recoverable failures. Verify assistive technology can learn about important updates without an unsolicited focus move, and that activation during a pending request avoids duplicate submissions where applicable. |
| `virtual-focus` | In virtualized or paged widgets, move the active item across a render boundary and change the available items. Verify that the focused item or active descendant exists when referenced, selection persists as intended, and position and set size are accurate when exposed. |
| `motion-state` | Trigger the interaction normally and with reduced motion. The final value, visual feedback, accessible state, focus and ability to continue remain correct when motion is shortened, interrupted or omitted. |

Choose expectations according to the widget. An action menu differs from a combobox that chooses a value, and an expandable navigation section may only need a disclosure button. A modal dialog has a different focus lifecycle from a nonmodal popover. Use the pattern's keyboard behavior and verify the actual rendered control. [APG guidance on keyboard interfaces](https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/), [APG combobox pattern](https://www.w3.org/WAI/ARIA/apg/patterns/combobox/), [APG modal dialog pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)

## Evidence

Record an ID of the form `interaction.<check-id>.<surface>.<widget>`, such as `interaction.dismissal.settings.member-picker`. Name the route and starting state, input method and action sequence. Capture the expected and observed focus target, visible result or accessible role/state. Use real keyboard, pointer or touch input and browser accessibility inspection as appropriate. For announcements and assistive-technology-specific behavior, record the browser and screen reader actually used. A screenshot, source review or static scan alone cannot establish runtime behavior.

Use `pass` for an observed match, `issue` for a reproduced failure, `blocked` when evidence cannot be collected, `pending` for an outstanding check, and `skipped` with the reason if a considered check does not apply. Keep issue details reproducible and link a Lab opportunity once it exists. After implementation, record fresh evidence for the affected widgets and for shared behavior that may have changed.
